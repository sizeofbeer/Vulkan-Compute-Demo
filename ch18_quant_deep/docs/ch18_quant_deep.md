# 第 18 章 · 深度量化（Q4_0 / Q8_0）

> 目标：掌握工业级 LLM 推理中使用的**分组量化**格式——Q4_0 和 Q8_0，理解 block 结构、fp16 scale、4-bit 打包/解包，并在 GPU 上实现**融合反量化 GEMM**。本章是 ggml/llama.cpp 量化体系的核心基础。

---

## 18.1 量化基础：为什么量化

### 18.1.1 显存瓶颈

大语言模型的首要瓶颈是**显存带宽**，而非算力。以 LLaMA-7B 为例：

| 精度 | 每权重 | 7B 模型所需显存 | 相对大小 |
|------|--------|-----------------|----------|
| FP32 | 4 字节 | ~28 GB | 1× |
| FP16 | 2 字节 | ~14 GB | 0.5× |
| Q8_0 | ~1 字节 | ~7 GB | 0.25× |
| Q4_0 | ~0.5 字节 | ~3.5 GB | 0.125× |

Q4_0 能把 7B 模型塞进 4GB 消费级显卡——这是 LLM 推理在本地运行的关键。

### 18.1.2 计算效率

量化不仅省显存，还能提升计算效率：

- **更少的带宽占用**：每次权重读取的数据量减少，缓解了**访存受限**（memory-bound）场景的瓶颈
- **更高的算术强度**：算术强度 = FLOPs / 访存量（字节），在 Roofline 模型中，算术强度越高，越接近算力天花板
- **融合反量化**：在 GPU 内核中就地解包反量化，避免物化中间 FP32 缓冲区，进一步减少访存

### 18.1.3 量化误差的容忍度

神经网络对权重的精度有天然的冗余性：

- 权重训练后通常具有一定的噪声鲁棒性
- 后续层的计算可以「平均化」量化误差
- 误差以 RMSE 衡量，Q8_0 通常 < 0.1%，Q4_0 通常 < 1%
- 配合 **per-channel** 或 **group-wise** 量化粒度，误差可进一步降低

## 18.2 Q4_0 格式详解

Q4_0 是 ggml 中最基础的 4-bit 量化格式，也是 llama.cpp 最初支持的核心格式。

### 18.2.1 Block 结构

```
Q4_0 Block（32 元素，20 字节，GPU 对齐版）：
┌─────────────────────────────────────────────┐
│ 字节 0-1 : d (fp16 scale)                   │  ← 2 字节
│ 字节 2-17: qs[16] (packed 4-bit, 2 元素/字节)│  ← 16 字节
│ 字节 18-19: padding                         │  ← 2 字节（对齐到 20 字节）
└─────────────────────────────────────────────┘
```

- **每 block 32 个元素**：权重矩阵沿 K 维度（行方向）每 32 个元素构成一个 block
- **d (fp16 scale)**：16 位浮点数，表示该 block 的缩放因子
- **qs (packed 4-bit)**：16 字节，打包 32 个 4-bit 有符号整数
- **padding**：2 字节填充，使 block 对齐到 20 字节（5 × uint32），方便 GPU 访问

### 18.2.2 量化过程

对于 block 内的 32 个权重值 w₀, w₁, ..., w₃₁：

1. 找最大绝对值：`maxAbs = max(|w₀|, ..., |w₃₁|)`
2. 计算 scale：`d = maxAbs / 7.0`（int4 最大正数为 7）
3. 量化每个元素：`qᵢ = round(wᵢ / d)`，钳制到 [-8, 7]
4. 打包：每两个 int4 值打包进一个字节——低 4 位为元素 2i，高 4 位为元素 2i+1

### 18.2.3 反量化过程

```
wᵢ ≈ float(qᵢ) × d
```

其中 `qᵢ` 从 packed 字节中解包：

```c
// 从字节中提取第 i 个 4-bit 值
byteIndex = i / 2;
nibbleShift = (i & 1) ? 4 : 0;
q = (byte[byteIndex] >> nibbleShift) & 0xF;
// 有符号 int4：大于等于 8 的值为负数
if (q >= 8) q -= 16;
```

### 18.2.4 压缩比

- 原始 FP32：32 × 4 = 128 字节
- Q4_0：20 字节（含 2 字节填充）
- 有效压缩比：128 / 18 ≈ 7.1×（不计填充为 128/18，计填充为 128/20 = 6.4×）
- 相比 FP16：32 × 2 = 64 字节 → 压缩比 64/20 = 3.2×

## 18.3 Q8_0 格式详解

Q8_0 是 ggml 中的 8-bit 量化格式，精度更高，适合对量化敏感的层。

### 18.3.1 Block 结构

```
Q8_0 Block（32 元素，36 字节，GPU 对齐版）：
┌─────────────────────────────────────────────┐
│ 字节 0-1 : d (fp16 scale)                   │  ← 2 字节
│ 字节 2-33: qs[32] (int8 数据)               │  ← 32 字节
│ 字节 34-35: padding                         │  ← 2 字节（对齐到 36 字节）
└─────────────────────────────────────────────┘
```

### 18.3.2 量化过程

1. 找最大绝对值：`maxAbs = max(|w₀|, ..., |w₃₁|)`
2. 计算 scale：`d = maxAbs / 127.0`（int8 对称量化，避免使用 -128）
3. 量化每个元素：`qᵢ = round(wᵢ / d)`，钳制到 [-127, 127]

### 18.3.3 反量化与压缩比

- 反量化：`wᵢ ≈ float(qᵢ) × d`
- 原始 FP32：128 字节 → Q8_0：36 字节 → 压缩比 128/36 ≈ 3.6×
- 相比 FP16：64 字节 → 压缩比 64/36 ≈ 1.8×

## 18.4 分组量化 vs 逐张量量化

### 逐张量量化（Per-Tensor）

第 11 章使用的量化方式：整个权重矩阵共享一个 scale。

```
scale = max|W| / 127
w_q = round(w / scale)
```

**缺点**：一个异常大的离群值会拉高 scale，导致其他所有值的量化精度下降。

### 分组量化（Group-Wise / Block-Wise）

Q4_0/Q8_0 采用的方式：每 32 个元素共享一个 scale。

```
block 0: scale₀ = max|w₀...w₃₁| / 7
block 1: scale₁ = max|w₃₂...w₆₃| / 7
...
```

**优点**：
- 每个 block 的 scale 自适应局部动态范围
- 离群值只影响其所在 block，不会"污染"全局
- 与逐张量相比，分组量化的 RMSE 通常低 5-10 倍

**代价**：每个 block 需要额外 2 字节存储 scale，增加了约 6.25% 的存储开销（Q4_0）。

## 18.5 融合反量化（Fused Dequantization）

### 为什么融合更高效

**分离路径**（Standalone Path）：

```
量化权重 (Q4_0) → 反量化内核 → FP32 权重 buffer → FP32 GEMM → 输出
                    ↑                              ↑
                一次额外写入                   一次额外读取
```

**融合路径**（Fused Path）：

```
量化权重 (Q4_0) ─┐
                  ├→ 融合反量化 GEMM 内核 → 输出
激活 (FP32) ──────┘
```

分离路径的代价：
1. **额外显存**：需要一个完整的 FP32 权重 buffer（K×N×4 字节）
2. **额外带宽**：反量化写入一次 + GEMM 读取一次 = 2 倍 FP32 权重流量
3. **量化白省了**：Q4_0 省了 7× 的权重存储，但分离路径让权重流量翻倍，净收益大打折扣

融合路径：
- 权重始终以 Q4_0 格式待在显存中
- 只在 GEMM 内层循环中按需解包反量化
- 解包后的值直接进入乘加累加器，**不写回显存**

### 在共享内存中的融合

本章的 `q4_0_gemm.comp` 使用 16×16 共享内存 tiling：

1. 每个线程加载 A 的一个 float 元素到 `As[][]`
2. 每个线程从 Q4_0 buffer 中解包并反量化 W 的一个元素到 `Ws[][]`
3. barrier 同步后，在共享内存中做 16 次乘加
4. barrier 后加载下一个 tile

这样，Q4_0 数据的读取发生在全局内存级别，但只读一次就被缓存到共享内存，共享内存中已是 float 格式——兼顾了带宽节省和计算效率。

## 18.6 ggml 中的反量化函数架构（2026-11 现状）

现行 ggml-vulkan 把反量化拆成三层，比「一个 `dequant_funcs` 文件 + `mul_mm` 里函数调用」更细：

| 层 | 位置 | 作用 |
|----|------|------|
| 数据结构 / 量化算法 | `ggml/src/ggml-quants.c`（旧的 `iq-quants.c` 已并入）、`ggml-cpu/quants.c` | 定义每种 block 的字节布局、`quantize_row_*` / `dequantize_row_*` |
| GLSL 公共片段 | `vulkan-shaders/dequant_funcs.glsl`、`dequant_funcs_cm2.glsl`、`dequant_head.glsl` | 被各 kernel `#include` 的解包/反量化函数；CM2 路径单独一份 |
| 独立反量化 kernel | `vulkan-shaders/dequant_<format>.comp`（26 个） | `dequant_q4_0.comp`、`dequant_q8_0.comp`、`dequant_q*_k.comp`、`dequant_iq*.comp`、`dequant_{mxfp4,nvfp4,q1_0,q2_0,tq1_0,tq2_0}.comp` 等 |

`mul_mm` 系列（`mul_mm.comp` / `mul_mm_cm1.comp` / `mul_mm_cm2.comp` / `mul_mmq_cm1.comp`）按权重量化类型选择 pipeline，并在加载权重 tile 时就地解包到共享内存 / 片段寄存器，共享内存中始终以 float 累加。155 个 `.comp` 模板由 `vulkan-shaders-gen` 在**构建期**用 glslc 编成 SPIR-V，仓库中没有预编译 `.spv`。

### 本章与 ggml 的对比

| 方面 | ggml 实现 | 本章实现 |
|------|-----------|----------|
| Q4_0 block 大小 | 18 字节（紧凑） | 20 字节（对齐） |
| 共享内存 tiling | 有 | 有（16×16） |
| Tile 尺寸 | 构建期按 shape 生成多套 | 固定 16×16 |
| 多格式支持 | 44 种 `GGML_TYPE_*`（Q4_0~Q8_0、K-quant、I-quant、MXFP4/NVFP4、TQ、Q1_0/Q2_0、F8_E4M3） | Q4_0, Q8_0 |
| 偏置融合 | 可选 | 可选（push constant 控制） |

本章的 20 字节对齐版在 GPU 上更高效（避免非对齐访问），代价是每 block 2 字节的额外开销（约 11%）。在 ggml 的紧凑版中，需要通过字节地址计算来访问数据，这需要更复杂的索引逻辑。新增格式里，NVFP4 用 E4M3 scale（4 blocks 一组），而本章 ch20 的 MXFP4 用 E8M0 scale——这是「同为 E2M1 但缩放粒度不同」的现成对比例子。

## 18.7 K-Quant 概述（通向第 20 章）

ggml 在 Q4_0/Q8_0 基础上设计了更高效的 **K-quant** 系列（Q2_K ~ Q6_K），作为第 20 章的铺垫：

### K-quant 的设计思路

K-quant 的核心思想是**超级块（super-block）**：

- **超级块**：256 个元素为一个超级块
- **子块**：每个超级块分为若干子块（如 Q4_K 分为 8 个子块，每子块 32 元素）
- **共享 scale**：超级块共享一个较大的 scale（fp16），子块使用较小的 delta（6-bit 或 4-bit）

### 各 K-quant 格式对比

| 格式 | 每权重位数 | 超级块大小 | 子块大小 | 特点 |
|------|-----------|-----------|---------|------|
| Q2_K | ~2.56 bit | 256 | 32 | 极端压缩，精度损失大 |
| Q3_K | ~3.55 bit | 256 | 32 | 中间选项 |
| Q4_K | ~4.55 bit | 256 | 32 | 流行选择，平衡精度与压缩 |
| Q5_K | ~5.55 bit | 256 | 32 | 高精度量化 |
| Q6_K | ~6.55 bit | 256 | 16 | 接近 FP16 精度 |

K-quant 相比 Q4_0/Q8_0 的改进：
1. 更高效的 scale 编码（6-bit 浮点量化，而非 fp16）
2. 超级块共享 scale 减少了 scale 的存储开销
3. 子块 delta 提供了足够的粒度

K-quant 是 ggml 在 v2.0+ 后的主力量化格式，将在第 20 章中详细实现。

## 18.9 动手实验

1. **修改 block 大小**：将 Q4_0 的 block 从 32 改为 64 或 16，观察量化误差和压缩比的变化。block 越大，scale 共享范围越大，压缩比越高但误差也越大。

2. **实现 per-channel 量化**：将 Q4_0 的 block 粒度改为整个 K 维度（即每列一个 scale），对比分组量化的误差差异。

3. **添加无偏置测试**：将 `hasBias` 设为 0，测试无偏置情况下的 GEMM 正确性。

4. **比较不同维度的性能**：将 M、N、K 改为不同的值（如 M=128, N=512, K=1024），观察不同量化格式的速度差异。

5. **实现 Q4_1 格式**：Q4_1 在 Q4_0 基础上增加了一个 fp16 的 min 值（偏移量），反量化为 `w = float(q) * d + min`。思考为什么加 min 可以降低量化误差。

6. **分析带宽受限 vs 算力受限**：使用本章的基准数据，结合你的 GPU 规格（显存带宽、FP32 峰值算力），判断各量化格式的瓶颈类型。

## 18.10 对照工业级

### ggml / llama.cpp

- **量化格式**：`GGML_TYPE_COUNT = 44`——Q4_0/Q4_1/Q5_0/Q5_1/Q8_0、Q1_0/Q2_0、Q2_K~Q6_K/Q8_K、IQ1~IQ4 系列、TQ1_0/TQ2_0、MXFP4/NVFP4、F8_E4M3
- **实现方式**：`ggml-vulkan` 中 `mul_mm*` 系列按权重类型选 pipeline；公共解包片段在 `dequant_funcs{,_cm2}.glsl`，另有 26 个 `dequant_<format>.comp` 独立 kernel；结构定义见 `ggml-quants.c`
- **优化技巧**：
  - 使用 `read_first_invocation` 或 subgroup 广播来加速 scale 读取
  - 在共享内存中解包和反量化，减少全局内存访问
  - 使用 `uint` 批量读取 packed 数据，减少指令数
  - 对高频路径使用 specialization constant 编译多个内核变体
- **性能**：Q4_0 在带宽受限场景下通常比 FP16 快 2-4 倍

### ncnn

- **量化格式**：int8 对称/非对称量化，支持 per-channel
- **实现方式**：在卷积和全连接层中融合反量化
- **特点**：利用硬件整数指令（dp4a）加速 int8 计算

### TensorRT

- **量化格式**：INT8 量化，支持 per-tensor 和 per-channel
- **校准**：需要校准数据集来确定 scale（而非简单的 max 法）
- **特点**：使用饱和量化（saturating quantization）而非简单的截断
